# Releasing Cupertino.Avalonia

Create releases from version tags on `main`. The workflow removes the leading `v` and passes the version to every build and package command with `-p:Version`. The shared default in `Directory.Build.props` is `0.0.0-local` for local builds. No project version needs to be edited for a release.

## Version propagation

For a tag such as `v0.2.0-preview`:

| Output | Version |
| --- | --- |
| NuGet package and assembly informational version | `0.2.0-preview` (the assembly can also include the source commit) |
| Assembly and file version | `0.2.0.0`, generated by the .NET SDK |
| Gallery About screen | `0.2.0-preview`, read from the library assembly |
| iOS, Android, and macOS app display version | `0.2.0`, derived from the same version without the preview suffix |
| App build number | `GITHUB_RUN_NUMBER` in Actions, or `1` locally |

The app settings are shared in `samples/Directory.Build.props`. Build numbers are numeric because app manifests cannot use a NuGet preview string as a build number. Override the build number with `-p:ApplicationVersion=42` when needed. Actions run numbers increase within each workflow, so keep app distribution on one workflow or supply a shared increasing counter if multiple workflows distribute the same app.

The release workflow currently publishes the library package and GitHub Release. When building a gallery app separately, pass the same `-p:Version` value to give its manifest and assemblies the release version. The gallery hides its version labels for an unversioned local build.

Dependency versions, the .NET SDK, and platform minimum versions remain pinned independently. A Cupertino release tag selects the version of this project; it does not upgrade Avalonia or other dependencies. The changelog still needs a section matching the release tag.

## One-time setup

Create a NuGet.org API key that can publish the `Cupertino.Avalonia` package. Add it to the GitHub repository as an Actions secret named `NUGET_API_KEY`.

## Prepare a release

1. Move the release entries from `Unreleased` in `CHANGELOG.md` into a versioned section matching the tag without its leading `v`, such as `## [0.2.0-preview]`. The release workflow stops if that heading is missing.
2. Make sure the intended commit is on `main` and its `build` workflow has passed.
3. Create and push an annotated tag whose version matches the changelog section:

```bash
git switch main
git pull --ff-only
git tag -a v0.2.0-preview -m "Release v0.2.0-preview"
git push origin v0.2.0-preview
```

Tags must use `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-PRERELEASE`. Preview tags create GitHub prereleases; stable tags create normal releases and are marked as the latest release.

The release workflow checks the tag, changelog and successful CI build, then rebuilds and tests the solution with the release version. It creates NuGet and symbol packages, prepares a draft GitHub Release, and publishes to NuGet.org before publishing the release.

Rerun a failed release from the same tag and commit. The workflow reuses the draft and skips package versions already on NuGet.org. Published NuGet versions cannot be replaced, even if unlisted; code changes need a new version and tag.

You can replace assets in a GitHub draft. Published assets cannot be replaced when release immutability is enabled. See the [NuGet publishing rules](https://learn.microsoft.com/en-us/nuget/api/package-publish-resource) and [GitHub release rules](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

## Build packages without releasing

Create local validation packages by passing a version explicitly:

```bash
ALLOW_DIRTY=1 ./build/pack-nuget.sh 0.2.0-preview
```

Published packages must be built from a clean working tree so Source Link refers to the exact packaged sources. Omit `ALLOW_DIRTY=1` for release candidates.
